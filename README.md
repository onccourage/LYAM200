# CQA — Conversation Quality Analytics (Freedom Broker Hackathon)

Прототип оценки качества работы операторов поддержки по диалогам (чаты и звонки, RU / KZ / EN).
LLM только классифицирует ответы по критериям и приводит реплики-доказательства; баллы считает
детерминированный `scoring.py`. **Чек-лист — это данные**: критерии, веса, шкалы и тексты хранятся в
JSON/БД и меняются через UI без правки кода и перезапуска; новая версия применяется к набору
инкрементально — в LLM уходят только изменённые критерии.

**Что есть:** загрузка набора по `group_id` (+ кэш, ручная загрузка JSON) · оценка диалога и пакетная оценка
набора с прогрессом и возобновлением · карточка диалога с переходом к реплике и плеером записи · апелляции
(контролёр / проверяющий) с пересчётом без LLM · редактор чек-листа с версиями · эталонная разметка и
отчёт согласия · аналитика по набору · сид готовых оценок для демо без API модели. 156 автотестов (`make test`).
Полный набор DEV (65 диалогов) оценён на `claude-sonnet-5-5`: 65/65 готово, 0 ошибок — результат в репозитории.

## Чек-лист и как его изменить

Чек-лист — это данные (JSON + версии в SQLite), а не код. Сид: `data/checklists/default_chat_v1.json`.
Схема критерия: `id` (стабильный), `code`, `section`, `title`, `description`, `type` (`binary | scale | flag`),
`weight` (у flag — 0), `na_allowed` + `na_condition`, `scale` (ступени с описаниями; верхняя = полный вес),
`flag_types` (подтипы нарушения для flag, например `insult`), `guidance` (правила для модели),
`channels`, `requires_audio`, `enabled`.

**Как изменить критерий (регламент контрольного часа):**
1. «Чек-лист» в шапке → раскрыть критерий (или «+ Критерий») → поменять текст, тип, вес, шкалу, N/A,
   каналы, аудио, guidance. Справа — живая сумма весов, ошибки и предупреждения (проверяет бэкенд).
2. «Сохранить как новую версию» → видно, какие критерии уйдут в LLM, а какие только пересчитаются.
3. «Применить ко всему набору» (или выбрать диалоги на экране набора) → пакетная оценка: в LLM уходит
   только изменённый/новый критерий, остальные берутся из кэша; итоги пересчитываются.
4. Проверить 2–3 карточки: в карточке видна версия чек-листа, доказательства, N/A, итог.

Старые версии неизменяемы; каждая оценка ссылается на `checklist_id + version` и не меняется задним
числом. Импорт/экспорт JSON — в редакторе. «Сохранить как новый чек-лист…» создаёт отдельный чек-лист;
«Использовать для оценки» выбирает, каким чек-листом оценивать.

API: `GET /api/checklists[/{id}[?version=]]`, `GET /api/checklists/{id}/versions`,
`GET /api/checklists/{id}/diff?from_version=&to_version=`, `POST /api/checklists/validate`, `POST /api/checklists`.

Тест `tests/test_checklist_change.py` эмулирует контрольный час через API (замена c05 на шкалу 0/2/4/6 с N/A и
весом 15) и проверяет сценарии: binary ↔ scale, новые ступени, смена веса (без LLM), разрешение/запрет N/A,
критерий только для звонков, критерий с аудио, новый flag-критерий со своими типами нарушений.

## Подсчёт баллов (`app/scoring.py`)

Чистая функция `score(checklist, answers, channel)`, только `Decimal`:
- binary: «Да» = вес, «Нет» = 0; scale: `вес × ступень / max(ступеней)`; flag — 0 баллов, отдельный `gross_error`.
- N/A (только при `na_allowed`) и критерии не своего канала исключаются, итог нормируется:
  `total = Σ баллов / Σ применимых весов × 100`; у каждого критерия видны `effective_weight/points`.
- Округление `ROUND_HALF_UP` только итога и итогов секций (знаков — `rounding` чек-листа).
- Нет применимых весов → `total = null` («не рассчитывается»), не 0. Грубая ошибка итог не обнуляет.
- Неверный ответ (N/A без разрешения, ступень не из шкалы, неверный тип) → `ScoringError`.
- `answer = null` — критерий на ручной проверке: в расчёт не входит, итог помечен `is_partial`.

## LLM-конвейер

`preprocess → prompt_builder → llm → validator → scoring → evaluations`:
- **preprocess**: реплики `m0…mN` (ID = индекс), факты: первая реплика оператора (не бота), язык клиента
  по его репликам, паузы ожидания ≥ `LONG_PAUSE_SEC`, системные события, канал/аудио.
- **prompt_builder**: неизменная рамка (`PROMPT_VERSION`) + блок критериев и JSON-схема ответа,
  сгенерированные из чек-листа. Вес в промпт не передаётся. Транскрипт — внутри `<transcript>`, как данные.
- **llm**: `LLMProvider` (Anthropic / OpenAI-совместимый endpoint / Fake для тестов). Ответ строго по
  JSON-схеме через structured outputs (`output_config.format`).
- **дробление по критериям** (`LLM_CRITERIA_PER_CALL`, по умолчанию 4): Anthropic отклоняет запрос
  («compiled grammar is too large») на ~6+ разнородных критериях в одной JSON-схеме ответа — проверено на
  реальном API (4–5 стабильно проходят, 6 падает независимо от состава типов). Критерии дробятся на группы,
  каждая группа — отдельный вызов, результаты сливаются по `criterion_id`; повтор после ошибки валидации
  тоже идёт только по упавшей группе, а не по всему набору критериев.
- **validator**: ответ допустим для типа, N/A только при разрешении, `message_id` существует, цитата —
  подстрока реплики, положительный ответ подкреплён репликой оператора/системы, «Нет» без цитат — с
  `checked_range`, N/A — с `na_reason`. Ошибка → один повтор только по ошибочным критериям → `needs_review`.
- **кэш критериев**: `hash(транскрипт) + hash(критерий) + модель + PROMPT_VERSION`. При новой версии
  чек-листа в LLM уходят только изменённые критерии; смена веса — только пересчёт.
- **requires_audio**: без аудио → N/A «нет аудиозаписи» (если разрешён), со звуком → `needs_review`.
- **Консенсус** (`LLM_SAMPLES` или выбор «3 / 5 проходов» на экране набора): диалог оценивается N независимыми
  проходами модели, по каждому критерию берётся ответ большинства (ничья — по средней уверенности), сохраняются
  голоса; уверенность не выше доли согласных проходов; расхождение подсвечивается в карточке и считается в
  аналитике («карта неуверенности» по критериям). Стоимость ×N — разумно для контрольных диалогов.
- **Прозрачность:** в карточке «Происхождение оценки» — сырой ответ модели по каждому вызову и точный промпт
  (рамка, критерии версии чек-листа, факты, транскрипт, JSON-схема); оценки, загруженные из сида, помечены
  «из сида» (автозагрузка сида по умолчанию выключена — `SEED_ON_START=0`).

Прогон из консоли:

```bash
python scripts/run_eval.py DEV                 # 5 диалогов разных каналов/языков
```

```bash

```

## Интерфейс

`http://localhost:8000` — чистые HTML/CSS/JS (ES-модули), без сборщика и CDN, отдаётся самим FastAPI.
- **Наборы и диалоги** (`#/d/{group_id}`): ввод `group_id` → «Загрузить набор», ручная загрузка JSON,
  список с фильтрами (канал, язык, статус оценки, грубая ошибка, поиск) и итоговым баллом.
- **Карточка диалога** (`#/c/{group_id}/{conversation_id}/m5`): слева транскрипт с якорями `m0…`
  (бот и система приглушены), справа итог, секции, бейдж грубой ошибки, версия чек-листа, модель, стоимость;
  по каждому критерию — ответ/ступень, баллы, исходный и эффективный вес, обоснование, доказательства.
  Клик по доказательству прокручивает к реплике и подсвечивает её; для «Нет» подсвечивается проверенный
  диапазон; для N/A показана причина; низкая уверенность и `needs_review` выделены.
  Для звонков — `<audio>`: клик по доказательству перематывает на `offset_sec` и запускает запись;
  если встроить нельзя — кнопка «Открыть запись» с тайм-кодом.
- Кнопки «Переоценить текущей версией» (неизменённые критерии из кэша) и «Переоценить полностью».
- Встраивание (Dynamics 365): `window.CQA_CONFIG = { API_BASE_URL: "https://..." }` или `?api=https://...`;
  все пути к статике относительные. Светлая/тёмная тема, адаптивная вёрстка.

## Пакетная оценка (`app/batch.py`)

- UI: на экране набора — «Оценить выбранные (N)» / «Оценить весь набор», опция «полностью, без кэша»,
  прогресс (обработано, оценено, требуют проверки, пропущено, ошибки, вызовы LLM, стоимость), «Остановить»,
  «Продолжить». Прогресс хранится в БД: после перезагрузки страницы подхватывается, после падения сервера
  задание помечается «прервано» и продолжается кнопкой.
- Параллельно `BATCH_CONCURRENCY` диалогов (семафор asyncio). 429/5xx/сеть повторяет SDK
  (`LLM_MAX_RETRIES`, экспоненциальная задержка); если модель недоступна для диалога целиком — повтор
  диалога `BATCH_RETRIES` раз с задержкой `BATCH_RETRY_BASE_SEC × 2^n`. Неудачная оценка не сохраняется.
- Возобновление: диалоги, у которых текущая оценка той же версии чек-листа со статусом «done», пропускаются.
  Новая версия чек-листа применяется к набору тем же запуском: в LLM уходят только изменённые критерии.
- API: `POST /api/batches` `{group_id, conversation_ids?, checklist_id?, checklist_version?, full?}`,
  `GET /api/batches/{id}`, `POST /api/batches/{id}/cancel|resume`, `GET /api/datasets/{group_id}/stats`.
- CLI: `python scripts/run_batch.py DEV [--full] [--ids ...]` (или `make batch GROUP=DEV`).

## Апелляции (`app/appeals.py`)

Ролей и авторизации нет: в шапке переключатель «Контролёр / Проверяющий».
- **Контролёр** в карточке диалога нажимает «Подать апелляцию» у критерия и пишет обязательный комментарий.
  На критерий — одна открытая апелляция; подать можно только на текущую оценку.
- **Проверяющий** на экране «Апелляции» открывает апелляцию: спорная оценка и шкала критерия, обоснование
  модели, доказательства (подсвечены в транскрипте, для звонков — плеер), комментарий контролёра.
  Решение: «Подтвердить» или «Изменить» (только допустимое для типа значение; N/A — если разрешён;
  для флага — тип нарушения) + обязательная причина.
- После решения итог пересчитывается `scoring.py` **без вызова LLM**. Хранятся и видны исходная оценка
  модели, решение, финальный результат, итог до/после, история (кто/когда/было/стало/почему); в карточке —
  «модель: X → после апелляций: Y». Критерий `needs_review` можно закрыть апелляцией — итог становится полным.
- API: `POST /api/appeals`, `GET /api/appeals?status=`, `GET /api/appeals/{id}`, `POST /api/appeals/{id}/resolve`.
- Ограничение: решения апелляций привязаны к оценке; переоценка диалога создаёт новую оценку без них
  (старая с историей сохраняется).

## Качество оценки: эталонная разметка

1. Подобрать и создать шаблоны (разнообразно: звонки, RU/KZ/EN, смешанный KZ+RU, длинные диалоги):
   `python scripts/gold_template.py DEV --suggest 18` → `data/gold/{conversation_id}.json` с `answers: null`,
   подсказкой допустимых значений и транскриптом. `--from-model` подставляет черновик из текущей оценки
   (помечается `draft_from_model` — каждый ответ нужно проверить, иначе эталон смещён в пользу модели).
2. Команда вручную заполняет `answers` (`"yes" | "no" | "na" | ступень`, для флага —
   `{"answer": "yes", "gross_types": [...]}`) и `annotator`.
3. `python scripts/eval_gold.py DEV [--evaluate]` — по каждому критерию: доля совпадений, каппа Коэна
   (binary/flag), MAE ступени и совпадение N/A (scale), матрица ошибок «эталон → модель», needs_review;
   разрез по языкам и каналам; MAE итогового балла (эталонный итог считается тем же `scoring.py`),
   совпадение флага грубой ошибки. JSON для слайда — `data/gold/_report.json`.
4. Итерации: правим `guidance` критериев в редакторе (это данные) или рамку промпта (`PROMPT_VERSION`),
   переоцениваем — кэш отправит в LLM только изменённые критерии — и повторяем `eval_gold.py`.

## Аналитика

Экран «Аналитика» (`#/analytics/{group_id}`, API `GET /api/datasets/{group_id}/analytics`) — по текущим оценкам
набора с учётом решений по апелляциям; все числа считает бэкенд (`app/analytics.py`):
- сводка: оценено, средний итог и медиана, доля диалогов с грубой ошибкой, требуют проверки,
  доля удовлетворённых апелляций, средняя стоимость диалога;
- «где операторы теряют баллы»: доля «Нет» (да/нет), доля оценок ниже максимума (шкалы), доля нарушений
  (флаги) среди применимых, отсортировано; в табличном виде — N/A, ступени, needs_review, низкая уверенность;
- распределение итогов, грубые ошибки по типам, качество по языкам и каналам;
- апелляции как оценка ошибок модели: доля изменённых решений, по критериям, средний сдвиг итога.

## Модель и стоимость

**Модели.** По умолчанию `claude-sonnet-5-5` через Anthropic API (вход $2 / выход $10 за 1 млн токенов;
дешёвый режим — `claude-haiku-5-5`, $0.10 / $0.50). Провайдер за интерфейсом `LLMProvider`: без правки кода
подключается любой OpenAI-совместимый endpoint — Google Gemini, vLLM, Ollama (пример в `.env.example`).

Особенности текущих моделей Claude, учтённые в коде: принудительный `tool_choice` и `temperature` на них
возвращают 400, поэтому формат ответа гарантирует structured outputs (`output_config.format` с JSON-схемой из
чек-листа), а повторяемость — схема + валидатор + кэш критериев; глубина рассуждений — `LLM_EFFORT`
(по умолчанию `medium`); при отказе классификатора безопасности включён серверный fallback
(`LLM_SERVER_FALLBACK=auto`); рамка промпта и блок критериев кэшируются (prompt caching).

**Учёт стоимости.** У каждой оценки сохраняются сырые ответы модели, токены входа/выхода (включая кэш промпта и
«размышления» модели) и число вызовов; стоимость = сумма всех вызовов, включая повторы и инкрементальные
переоценки, по ценам из `.env`. В карточке — стоимость оценки, на экране набора — средняя стоимость диалога и
сколько потрачено всего.

**Фактическая стоимость на DEV, `claude-sonnet-5-5`** (полный прогон всех 65 диалогов, `data/seed/DEV.json`):
2 вызова на диалог (дробление по 4 критерия), в среднем **~10.8 тыс. токенов входа и ~1.4 тыс. выхода**
(звонки и длинные RU-диалоги — вход больше, до 115 реплик в транскрипте) — **≈$0.0202 за диалог**, весь
набор **≈$1.31**. 65/65 оценены, 0 ошибок, ни один критерий не ушёл в `needs_review`; средний итог 73.75,
грубая ошибка — у 5 диалогов. `claude-haiku-5-5` по тем же токенам — на порядок дешевле, но без проверки
качества. Замена одного критерия на наборе — ещё ~1 короткий вызов на диалог (не на все, если группа без
изменений — только пересчёт).

**Контрольный час (репетиция на DEV, реальная модель):** замена c05 на шкалу 0/2/4/6 с N/A → в LLM ушёл только
новый критерий, 4 диалога за 10 с; смена веса и выключение критерия — только пересчёт, без LLM; новый
flag-критерий «только для звонков» — 1 вызов, 3 с. Скрипт: `scripts/rehearse_control_hour.py`.

## Ограничения

- **Оценивается только текст.** Критерии, требующие звука (`requires_audio`), без записи получают N/A
  (если разрешён), со звуком — «требует прослушивания»: модель не делает вид, что слышала запись.
- **Записи звонков.** `audio_url` организаторов — HTML-страница; бэкенд берёт из неё mp3-ссылку (живёт ~1 ч).
  Сдвиг записи относительно транскрипта подобран по 5 звонкам DEV (timestamp реплики звонка — конец фразы;
  запись начинается позже первого события на 9–30 с) — перемотка точна примерно до секунды-двух.
- **Язык клиента** определяется эвристикой по буквам; короткие казахские реплики без специфичных букв
  неотличимы от русских — окончательно язык оценивает модель.
- **Апелляции** привязаны к конкретной оценке: переоценка диалога создаёт новую оценку без решений
  проверяющего (старая с историей сохраняется).
- **Ролей и авторизации нет** — переключатель «Контролёр / Проверяющий» в шапке (по ТЗ).
- **Дробление критериев** (`LLM_CRITERIA_PER_CALL=4`) подобрано под дефолтный чек-лист (8 критериев, проверено
  вплоть до 5 в одном вызове на реальном API). Чек-лист со значительно более сложными критериями (много
  ступеней шкалы, много типов нарушений) теоретически может потребовать меньшего значения — ошибка API
  («compiled grammar is too large») в этом случае явная, а не тихая.
- **Альтернативные провайдеры** (Gemini, vLLM, Ollama) подключаются без правки кода, но не проверялись на
  полном наборе: у бесплатного Gemini — 20 запросов в день на модель; `gemini-3.5-flash-lite` для оценки
  не годится (на проверке ставил всем диалогам максимум). Сдача ориентирована на Anthropic API.
